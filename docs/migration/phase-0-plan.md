# Guide Platform Migration Plan and Progress

Last updated: 2026-09-09

## Current Status

Phase 0 is in progress. Step 0.1, which establishes the migration baseline,
is complete. The remaining Phase 0 work documents the existing behavior,
data, API surface, acceptance criteria, and prioritized migration backlog.

| Step | Status | Outcome |
| --- | --- | --- |
| 0.1 Establish the current baseline | Complete | Repository, build baseline, local configuration, and known gaps recorded. |

## Migration Sequence

```text
Phase 0: Establish migration baseline and plan
    |
Phase 1: Engineering foundation and Console restructuring
    |
Phase 2: Maps
    |
Phase 3: Personas, plugins, and skills
    |
Phase 4: Tour task CRUD and authoring
    |
Phase 5: Agent application and task synchronization
    |
Phase 6: Parallel operation, acceptance, and legacy retirement
```

The core business dependency order is:

```text
Infrastructure and demo identity
    -> Maps
    -> Personas, plugins, and skills
    -> Tour tasks and publishing
    -> Agent download and synchronization
    -> Legacy retirement
```

#### Known Baseline Gaps

- `apps/agent` is planned in the architecture but does not exist. Accordingly,
  `pnpm dev:agent` cannot run yet.
- `services/api/prisma/` contains a schema and seed script but no committed
  Prisma migrations.
- The project has no automated test files. The Console's Vitest command is
  therefore red until at least one test is added or the no-test-files behavior
  is deliberately configured.
- PostgreSQL and the API database connection have not been checked because the
  local Docker daemon is stopped.
- The legacy static applications and the new Console coexist. The legacy
  implementation remains the behavior reference during migration.

### 0.3 Inventory Screens, Routes, and User Flows

Status: Not started

### 0.4 Map Legacy Data to Prisma

Status: Not started

| Legacy concept | Prisma destination |
| --- | --- |
| Map | `MapAsset` |

draft migration scope, encrypted plugin configuration handling, and data import
or export behavior.

### 0.5 Inventory API Contracts

Status: Not started

Create `docs/migration/api-contract-inventory.md`. Start with the implemented
API surface:

```text
GET /api/v1/health
GET /api/v1/runtime
GET /api/v1/tour-tasks
```

Then list the required endpoint families for `maps`, `personas`,
`mcp-plugins`, `skills`, `tour-tasks`, and `agent-sync`. Each proposed endpoint
must define request fields, response fields, error behavior, authorization,
pagination needs, and version/concurrency behavior. Shared schemas belong in
`packages/contracts`.

### 0.6 Define Migration Acceptance Criteria

Status: Not started

Create `docs/migration/acceptance-checklist.md`. Define P0 verification for:

```text
Create map
    -> create tour task
    -> add points and actions
    -> save draft
    -> publish task
    -> Agent downloads task
```

Also define criteria for persona creation, plugin or skill binding, and persona
selection during task authoring. For every flow, cover default, loading, empty,
error, validation, cancellation, deletion confirmation, keyboard, narrow-screen,
data refresh, and persistence behavior.

### 0.7 Freeze Scope and Create the Migration Backlog

Status: Not started

Create `docs/migration/phase-0-backlog.md` and prioritize work by dependency:

| Priority | Initial items |
| --- | --- |
| P0 | Map CRUD, task CRUD, point/action persistence, draft and publish flow. |
| P1 | Persona management, MCP plugin management, Agent download API. |
| P2 | Advanced map editing and real-time execution status. |
| Blocked | Booster SSO and cloud-skill integration pending sandbox documentation and credentials. |

Record these scope rules:

- Do not delete the legacy applications during migration.
- Implement new behavior in the new stack by default.
- Limit legacy changes to necessary fixes.
- Perform new-versus-legacy acceptance after completing each business domain.
